**PyPI: an upload does not claim a name an upstream lists, its name is a PEP 503 name and its file is the archive its extension says (audit A101, A079, B11)** — with an upstream configured, the first twine upload of a project outside `curation.internal_namespaces` claimed the name as hosted even when an upstream listed it, so the public versions stopped being served and the uploaded files replaced them without release-age or quarantine checks. That first upload now asks the upstreams for the name's index (cached for `pypi.metadata_ttl`, single-flight) and is a 409 while one lists a file under it, the upstream's 5xx while none answers, and claims the name only when every upstream answered that it has none; projects already hosted or internal are unchanged. `nora_pypi_mixed_project_uploads_total{upstream_lists}` now counts `yes` for a refused upload and `no` for a claim (`unknown` is gone). An upload whose name does not normalize to `[a-z0-9]` runs joined by `-` is a 400, and the simple project page escapes the project name in its file links as it does on the page. A `.whl`, `.zip` or `.egg` that is no zip, or a `.tar.gz` or `.tgz` that is no gzip stream, is a 400 at upload instead of failing at install. Operators: before rolling out, add to `curation.internal_namespaces` every name you publish here that an upstream also lists (the earlier `[SECURITY] upload to a project outside curation.internal_namespaces` WARN lines and `upstream_lists="yes"` show them); the first upload of a new private name now costs one upstream index lookup and fails while every upstream is down.
