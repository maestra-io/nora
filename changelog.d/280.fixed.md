**Docker GC: a sweep in another process never deletes a layer a push was just told exists (Maestra fork, audit A030)** — the confirmation a blob `HEAD`, a mount or a manifest push's layer check gives a client lived only in the memory of the serving process, so a sweep in another one (the other pod of a rolling update, which runs its first pass at boot, or `nora gc --apply`) could delete an old orphaned layer after a re-push or re-tag got 201, leaving the image without it. For a blob within an hour of `gc.grace_secs` or older, the confirmation is now also written to storage (`.nora-gc-confirmed/<key>`, at most once per key per half grace per process), and every sweep writes a delete intent (`.nora-gc-deleting/<key>`) before it reads that confirmation: the sweep keeps a blob confirmed within the grace, and a confirmation that meets a live intent answers "absent", so the client uploads the layer again (`HEAD` 404) or its push is refused (`MANIFEST_BLOB_UNKNOWN`) instead of storing a broken image. An intent older than 5 minutes (a crashed sweep's) is ignored, a sweep that stalls for half of that keeps the blob, ages are judged from the start of the pass, and each applied pass removes the markers whose blob is gone. Fresh blobs cost nothing extra; a confirmation of an old blob costs one put and two stats, a swept Docker orphan a put, a stat and a delete. `nora gc --apply` beside a running server is safe only while that server runs with `gc.enabled = true`. The first rollout of this release is not yet covered: the old pod writes no markers.
