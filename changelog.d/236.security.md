**Upstream clients refuse loopback and private addresses (Maestra fork, maestra-io/nora#236, audit A034)** — the server's shared, no-redirect and same-origin upstream clients (every proxied format, the npm tarball walk, the Docker token exchange and the OIDC/Teleport JWKS fetches) followed a redirect from a configured upstream to any address, loopback, private, link-local and metadata included, and served and cached the answer. A redirect hop to such an IP literal now fails the fetch, and a host name is connected only to its addresses outside those ranges (a name that resolves only into them fails, 502); with an outbound proxy set, only the IP-literal check applies and the proxy must filter names. New `server.allow_private_upstreams` (env `NORA_ALLOW_PRIVATE_UPSTREAMS`, default `false`) restores the previous behaviour for deployments that proxy an internal registry or fetch an in-cluster JWKS; at startup NORA warns about each configured upstream or JWKS host that resolves only to blocked addresses. The upstream URL as configured is not checked when it is an IP literal; `nora mirror` and `nora healthcheck` stay unguarded.
