**Go `@v/list`, `@latest` and revision queries leave out the versions the `.zip` gate holds for `min_release_age` (Maestra fork, #292)** — under `curation.mode = "enforce"` the Go proxy listed and resolved versions its own `.zip` gate then refused, so `go install golang.org/x/vuln/cmd/govulncheck@latest` resolved v1.10.0 the day it was released and failed on a 403 for three days. A proxied module's `@v/list` now leaves out the versions the gate holds (each major.minor's releases and pre-releases are dated from the newest down to the first admitted one, with the gate's own date: `.info` `Time`, NORA's first sight, `[go] attested_dates`), `@latest` whose version is held answers the newest admitted listed version (release before pre-release; none: the `.zip` gate's 403), and a branch or revision query resolving to a held version answers that 403 too (not 404, which a `GOPROXY=…,direct` client takes as "fetch it elsewhere"). `[curation.go] allow` entries stay offered; a held version listed below an admitted one in its major.minor stays listed (its `.zip` is still 403); the dates are read only with `trust_upstream_dates` (without it nothing is left out); audit mode only logs; internal modules are not filtered. Operators: the first listing of a module after the upgrade may fetch the `.info` of each major.minor's newest versions.
