**Password lockout holds for passwords sent at once; credentials in the Basic username are not logged; htpasswd passwords over 72 bytes are refused (audit A019, A020, B14, maestra-io/nora#245)** — the lockout read the failure count before a password was checked and counted the failure after, so many different passwords for one account sent together were all checked by bcrypt before any failure counted. Now a password bcrypt will check first takes a slot: an account (and its address) may have only as many different unchecked passwords in flight as it has attempts left before its lockout. A further one is answered 429 with `Retry-After: 1`, counted in `nora_auth_rejected_total{reason="checks_in_flight"}`, neither logged nor counted as a failure. The same password sent by many requests (a parallel pull) shares one check, and API tokens, OIDC and remembered verdicts take no slot. The rejection and lockout log lines now write `<credential-in-username>` instead of a Basic username shaped like an API token, a session token or a JWT; lockout keying is unchanged. An htpasswd password longer than 72 bytes used to match on its first 72 bytes (bcrypt reads no more) and is now refused: an htpasswd account whose password is longer must get one of 72 bytes or fewer.
