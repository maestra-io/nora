**Proxy fills and imports no longer leave proxy provenance on a hosted or imported npm tarball or PyPI file (Maestra fork, audits A031, A032, A075, A078)** — `nora import` committed an npm tarball or PyPI file over a proxy-cached copy without removing the cache's provenance record (and, for npm, its `.sha256` sidecar), so gc could evict the imported file as proxy cache and a large npm tarball answered 500 on its stale sidecar; an npm proxy fill decided once, before the upstream fetch, that the package was not published, and then cached the upstream's bytes and record over a version published meanwhile; a PyPI fill wrote its sidecar, hash marker, core metadata and provenance marker after releasing the file's lock, over an upload that had replaced the file. Now the import deletes the provenance record right after it commits an npm or PyPI file (a failed commit leaves the cached copy a cache) and writes npm's sidecar with the imported digest; the npm fill (buffered and spooled) takes the package lock and then the tarball lock, as a publish does, and caches only while the package is still not published here; the PyPI fill writes its records under the file's lock again, none when the stored pin is another digest or the file is the project's own, and only its provenance marker when the store does not answer the pin read. These locks are per process: they order a server's fills against its own publishes, uploads and gc, while a `nora import` run is a process of its own. gc selects no npm tarball that has a version document and no PyPI file recorded under `pypi-own/` (PyPI is skipped for the pass when that listing fails), and asks again under the file's lock before it deletes, or lists in a dry run, any npm or PyPI file: one that is claimed by then, whose pin differs from its record's digest or whose pin read the store does not answer, is kept, and its size comes off the bytes the pass must free. Operators: no request changes status; fills of one npm package now serialise on the package lock; a fill whose package's published state cannot be read caches nothing (a refetch next time); the proxy cache can sit slightly over `proxy_cache_max_bytes` by such kept copies, counted in the eviction log line. Copies already damaged are kept, not repaired.
