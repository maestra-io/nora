**Shutdown, connection stall, hf cache cap and restore marker follow-ups (Maestra fork, maestra-io/nora#299, review R15, R16, R20, R21)** — the Teleport listener (`server.teleport_port`) serves the whole app but stopped only after the main listener had drained and then gave its requests 1 s; it now stops at the shutdown signal with the main listener, drains for `server.shutdown_timeout`, and the shutdown waits for it before stopping the schedulers. The `server.body_idle_timeout` stall detector counted a wait on the client only between response frames, so a response held in memory as one frame (a cached artifact under `stream_threshold_mb`, a large packument) that the client never read kept its connection and its `max_connections` slot open with no deadline; a socket write that makes no progress now counts as a wait on the client too, so such a connection is closed at the timeout; over HTTP/2, where such data can sit in the stream's buffer behind a flow-control window the peer never opens, the keep-alive close of the connection now waits at most `body_idle_timeout` before it drops it. With `hf.enabled`, start now warns that Hugging Face files larger than the smaller of `server.proxy_max_artifact_mb` and `server.spool_max_mb` are served from the upstream on every request and never cached (0 on both = no limit). A `.nora-tokens/restore_in_progress` marker left by a failed `nora restore` made a later plain restore treat the store as having no tokens and write back every archived token, revoked ones included, and a revoke of a store's last token made it look fresh the same way; a revoke now writes `.nora-tokens/revoked/<id>` before it deletes the record, a plain restore never writes a record so marked (it checks before and after each write, so a revoke during the restore is caught too, and first deletes a marked record an earlier failed run left, and last one written from an archive that held both) and counts it as left out, a legacy-hash migration on verify never rewrites a marked record, and every finished restore drops the marker, `--include-tokens` runs too (which still restore every record). **Behaviour change:** a revoke writes one small object per token, kept for good and carried by `nora backup` and `nora migrate`; a revoke of an id with no record answers 404 without writing it.
