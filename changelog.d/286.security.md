**An unanswered RubyGems date lookup is judged, and a successful one dates the whole gem (Maestra fork, audit A063)** — a `.gem` or gemspec whose `/api/v1/versions/<name>.json` lookup got no answer (a transport error, 429, 5xx, a body that does not parse) was served undated, so `min_release_age` let it through, and a file cached that way was never dated later. Such a lookup now goes through `[curation.gems] unknown_date`: `log` (the default for this release) serves it with a `[SECURITY] min-release-age unknown date` line and `nora_curation_unknown_release_date_total{registry="gems"}`, `hold` refuses it (403) without fetching or caching it. A 404, or an answer that does not list the version or platform, still leaves the file undated, so ambiguous file names keep working. An answer that dates the file is kept at `gems/dates/<name>.json`, so the gem's other files make no API call. Operators: no change under the default `log`; watch the counter, then set `unknown_date = "hold"` (`NORA_CURATION_GEMS_UNKNOWN_DATE=hold`). Under `hold`, a cold install of an uncached gem fails while the RubyGems API is down or rate-limited; the bypass token or a `[curation.gems] allow` entry unblocks a build.
