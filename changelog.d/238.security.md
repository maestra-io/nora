**Docker writes to an upstream's pull-through name are refused, every write names its principal, and a blob mount honours curation (Maestra fork, maestra-io/nora#238)** — a name a `prefix`, `namespaces` or a served registry host routes to an upstream is that upstream's pull-through, yet a credential with write access could push, upload, mount or delete under it, and a push replaced the upstream's tag for every puller. Such a write now gets 403 `DENIED` unless the canonical name is in `curation.internal_namespaces`; reads are unchanged, an image already stored under such a name keeps being served, and names the fallback chain serves (bare names under `default_action = "allow"`) still take writes. Operators can no longer purge a cached proxied tag with `DELETE /v2/<prefix>/…`, and a deployment that pushes under a routed name must list it in `curation.internal_namespaces` first. Docker blob push, mount, manifest push, manifest delete and blob delete were audited with the constant actor `api`; they now carry the authenticated principal (`anonymous` without one), so an audit query filtering docker events on `actor = "api"` stops matching. A cross-repository blob mount (`POST …/blobs/uploads/?mount=&from=`) now asks curation about the source name as a GET of the blob would, with the same bypass token: a blob curation refuses to serve from the source is not copied, and the mount falls back to an upload session (202).
