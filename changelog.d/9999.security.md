**Proxy fills and imports never leave proxy provenance on a hosted or imported npm tarball or PyPI file (Maestra fork, audits A031, A032, A075, A078)** — `nora import` committed an npm tarball or PyPI file over a proxy-cached copy without removing the cache's provenance record (and, for npm, its `.sha256` sidecar), so gc could evict the imported file as proxy cache and a large npm tarball answered 500 on its stale sidecar; an npm proxy fill decided once, before the upstream fetch, that the package was not published, and then cached the upstream's bytes and record over a version published meanwhile; a PyPI fill wrote its sidecar, hash marker, core metadata and provenance marker after releasing the file's lock, over an upload that had replaced the file. Now the import commits npm and PyPI files under the key's publish lock, deleting the provenance record first and writing npm's sidecar with the imported digest; the npm fill (buffered and spooled) takes the package lock and then the tarball lock, as a publish does, and caches only while the package is still not published here; the PyPI fill writes its records under the file's lock again, only while the stored pin is its digest, and its provenance marker only when the file is not the project's own. gc no longer evicts an npm tarball that has a version document or whose pin differs from its record's digest (re-checked under the lock), nor a PyPI file recorded under `pypi-own/`, and skips PyPI eviction for the pass when that listing fails. Operators: no request changes status; fills of one npm package now serialise on the package lock; a fill whose package's published state cannot be read caches nothing (a refetch next time); the proxy cache can sit slightly over `proxy_cache_max_bytes` by such kept copies, counted in the eviction log line. Copies already damaged are kept, not repaired.
