**A kept release-date answer never passes a version it lacks; the date memo is bounded per registry; an unlisted npm version fetches its packument once (#293, audit R01, R06, R19)** — the upstream release-date memo (#235) reused, for 60 s, a kept answer that lacked the wanted version (RubyGems versions API, registry.terraform.io `/v2`) or a kept "not on Central" for a Maven file, so a version published inside that window was judged with no date and, with the digest quarantine only observing, served and cached undated. Such a reused answer is now marked unasked, and the version is held as released now (refused by `min_release_age` in enforce mode), whatever `[curation.<registry>] unknown_date` says, until the lookup is asked again after the window; a fresh answer and an unanswered lookup are judged as before. The memo also kept one 1024-key map for every registry and cleared it whole once full, so Maven's per-file keys flushed the gems and terraform entries, in-flight lookups included: each registry now keeps its own 1024 keys, drops its expired then its longest-finished key, and never one in flight. With `server.trust_upstream_dates`, an npm tarball of a version the upstream packument does not list fetched that packument twice (#259); the packument the date lookup fetched now stands for the tarball step's refetch.
