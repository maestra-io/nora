**API token lifecycle: Teleport owners are namespaced, admins list and revoke tokens, every revoke is audited, mint errors stay generic (Maestra fork, audits A023, A089, A024, B26, #284)** — a Teleport identity is now `teleport:<username>`, so the tokens it mints, lists and revokes in the UI are owned by a name no htpasswd account or admin mint can hold (`POST /api/v1/admin/tokens` answers 400 for an owner starting with `teleport:`); before, a Teleport user whose name matched a service owner saw and could revoke that owner's tokens. Tokens a Teleport user minted before this release keep working but are owned by the bare name: they no longer show in that user's UI list and the user cannot revoke them; an admin can. Audit entries and the setup page name Teleport actors `teleport:<name>`. New admin routes behind the `/api/v1/admin/` gate: `GET /api/v1/admin/tokens[?user=]` lists token metadata (never a hash), `DELETE /api/v1/admin/tokens/{id}` revokes one (204, 404, 503) and `DELETE /api/v1/admin/tokens?user=` revokes every token of one owner and answers the ids revoked (list first: pipelines can share an owner); a namespace-scoped admin gets 403. `auth.teleport.max_token_ttl_days` (`NORA_AUTH_TELEPORT_MAX_TOKEN_TTL_DAYS`, unset by default, 0 unsets) caps the lifetime of tokens a Teleport user mints in the UI; existing tokens keep their expiry. Every successful revoke, on `POST /api/tokens/revoke`, the UI and the admin routes, now writes a `token_revoke` audit entry (actor, owner, route, `id=<file_id>`, never the token). A mint whose record cannot be stored answers a fixed 500 body on every route and a failed UI revoke a fixed 503 body, with the storage error in the server log only; before, the body carried the storage error text.
