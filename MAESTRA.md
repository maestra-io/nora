# Maestra fork of nora

Real GitHub fork of [getnora-io/nora](https://github.com/getnora-io/nora); tracking issue maestra-io/issues-maestra#1442.

- `main` is an untouched mirror of upstream `main`: fast-forward only, never commit to it.
- `maestra/main` (default branch) is upstream `main` plus our commits. All our work lands here via PRs.

Maestra-only changes (not upstream):
- Hosted NuGet feed retention/repair: `[nuget] hosted_pr_retention_days` (`NORA_NUGET_HOSTED_PR_RETENTION_DAYS`, default 30, 0 = keep all) and `hosted_pr_keep_last` (`NORA_NUGET_HOSTED_PR_KEEP_LAST`, default 20) expire `X.Y.Z-pr.*` versions in a periodic pass (retention interval and dry-run) that also handles blob dirs no state document names (>1 h old): a complete one (package + a `.nuspec` matching its path: a version the document lost to a write from another process) is written back into the document, an incomplete one is deleted (R2-08); `nora nuget rebuild <id>` rewrites `nuget/hosted-meta/{id}.json` from the stored nuspecs, keeping versions pushed while it ran; a push, `nora import` and rebuild re-read the document right before writing it (R2-35); `POST /api/v1/admin/reindex` also re-reads hosted state documents.
- `nora import` hosts npm, NuGet and PyPI (C73): each verified file goes through the publish internals (`npm::publish_versions`, `nuget::hosted::import_package`, `pypi::store_file`), so it is served like an upload (npm `latest` = highest imported release; publish times are the import time; NuGet unlisted and PyPI yanked state are not carried). NuGet state documents written behind a running server are served after `POST /api/v1/admin/reindex`. `curation.internal_namespaces` is not applied to an import (hosted source repos only).
- `[storage] s3_credentials_dir` / `NORA_STORAGE_S3_CREDENTIALS_DIR`: S3 credentials (`access_key_id`, `secret_access_key`, optional `session_token`) read from files and re-read every 60 s, for the rotating STS-style R2 creds Vault mints (packages.maestra.io, issues-maestra#1442).
- `[auth] read_only_users` / `NORA_AUTH_READ_ONLY_USERS`: htpasswd accounts that authenticate as `read` (pull only, read tokens only); every self-service token mint is capped at the caller's own role.
- An enabled OIDC provider with an empty `audience` is a config warning, and an error under `NORA_CONFIG_STRICT`.
- `[auth.teleport]` (`nora-registry/src/auth/teleport.rs`): web UI identity from Teleport application access. On UI paths (`/`, `/ui*`, `/api/ui*`, `/api-docs*`) a `Teleport-Jwt-Assertion` from a TCP peer in `trusted_proxies` is verified against `jwks_url` (`iss` = `issuer`, `aud` = `audience`, ES256/RS256, JWKS cached `jwks_cache_secs`, refetched on an unknown `kid`, stale on fetch failure). Identity = the `username` claim; `roles` ∩ `write_roles` → `write`, else `read`; never `admin`. `require_for_ui = true`: UI paths without that identity answer 404, and a 401 to a browser (`Sec-Fetch-Mode`, or `text/html` first in `Accept`) carries no `WWW-Authenticate`, so no password dialog. Registry paths ignore the header. Keys: `enabled`, `jwks_url`, `issuer`, `audience`, `trusted_proxies` (IP/CIDR string), `write_roles`, `require_for_ui`, `leeway_secs` (60), `jwks_cache_secs` (300); each also `NORA_AUTH_TELEPORT_<KEY>` (lists comma-separated).
- `[auth] htpasswd_allowed_peers` / `NORA_AUTH_HTPASSWD_ALLOWED_PEERS`: TCP peers whose htpasswd password is checked (unset = all, as upstream). Any other peer: no bcrypt, `/api/tokens*` → 403, Basic carries only `nra_` tokens and OIDC JWTs.
- Disk spool budget (R2-05): `[server] spool_dir` (`NORA_SPOOL_DIR`, default `{storage.path}/tmp`) holds `proxy-spool/`, `nuget-uploads/` and `pypi-uploads/`; `spool_max_mb` (`NORA_SPOOL_MAX_MB`, 4096, 0 = none) bounds them together (over it: 503 + `Retry-After`, never waited on), `proxy_max_artifact_mb` (`NORA_PROXY_MAX_ARTIFACT_MB`, 2048, 0 = none) caps one proxied body on `Content-Length` and running count (507); a spool never takes the filesystem below 64 MiB free. A local spool failure is 507 (ENOSPC) or 500, never a 502, and every refusal counts in `nora_spool_failures_total{registry,reason}`. All three dirs are swept for orphans (>4 h) at startup and every 5 min. Proxied artifacts time out on response headers and on a body stall of `proxy_timeout`, not on total download time.
- `/ui/setup` (sidebar "Developer setup", dashboard card "Set up your machine"): the en/ru guide to connecting dotnet/NuGet, npm (Yarn, pnpm), pip, uv and Poetry, with macOS/Windows tabs (choice kept in `localStorage`), copy buttons and a highlighted `<TOKEN>`. Every registry URL comes from `public_url`; the cooldown section shows the enforced `min_release_age` per NuGet/npm/PyPI and `curation.internal_namespaces` from the live config. `[server] ui_docs_login_url` / `NORA_UI_DOCS_LOGIN_URL` (default `https://packages.teleport.maestra.io`) is where the page sends people to sign in and mint a token. Same auth as the rest of the UI. Tool sections are tabs (NuGet / npm / PyPI; `#nuget`, `#npm`, `#pypi` deep-link, choice kept as `nora_setup_tool`); Cooldown and Troubleshooting stay always visible. "Generate token" in the token card posts to `/api/ui/tokens/create` with `ui=setup` (same auth, OIDC 403, role capped at the caller's: `write` offered only to a write identity): JS gets JSON `{token}` and fills every `[data-token-slot]` in the page (never stored; reload = placeholders); a JS-free post is accepted on `Sec-Fetch-Site: same-origin` and answers the filled page. Token responses are `Cache-Control: no-store`.
- `/ui/tokens*` and `/api/ui/tokens*` answer 403 to an OIDC (workload) identity: a CI JWT cannot exchange itself for a long-lived, unscoped `nra_` token.
- The auth lockout (5 failures, then 1 s doubling to 15 min) is keyed per client IP and username and counts htpasswd passwords only: a Bearer credential (`nra_` token, JWT, also sent as the Basic password) is never counted nor refused by it.
- `/health` answers 503 (`status: stalled`) once the 30 s maintenance loop has not ticked for 300 s: readiness trusts the storage verdict only that loop refreshes, so a dead loop now restarts the pod instead of leaving it NotReady.
- `[server] keep_alive_timeout` / `NORA_KEEP_ALIVE_TIMEOUT` (default 120 s, 0 = no limit): an idle HTTP/1 keep-alive connection waits this long for its next request; `header_read_timeout` (30 s) bounds only a head that has started (and a connection's first). Upstream closes idle connections at the header timeout, under traefik's 90 s idle reuse (502 on publishes).
- `[server] internal_port` / `NORA_INTERNAL_PORT` (unset = upstream behaviour): a second listener on that port serves the detailed `/health`, `/ready` and `/metrics`; the main port then answers `/metrics` 404 and its `/health` carries only `status` (no version, storage backend, registries, breaker state). Chart: containerPort/Service port `internal`.
- Cargo features `rpm` and `deb` (default on): `--no-default-features` builds without those registries, their parsers and the rpgp index signer; a config enabling them on such a build logs an error and does not mount them. Our release image is built that way (`CARGO_FEATURES=--no-default-features`).
- Builds are `--locked` (Dockerfile, CI); Swagger UI comes from the `vendored` feature of `utoipa-swagger-ui` (crates.io, checksummed), not a build-time GitHub download.
- `[curation.<registry>] allow = [...]` / `NORA_CURATION_<REGISTRY>_ALLOW` (comma-separated): versions exempt from `min_release_age` only. Entry forms: `name@version` (that exact version; npm `@scope/name@1.0.0`), `name` or `name@*` (every version of that package), `prefix*` or `prefix*@*` (every version of every package whose name starts with `prefix`, e.g. `Microsoft.NETCore.*`; `prefix*@1.2.3` = that version of each). The `*` is a plain prefix match at the start of the name, so `Microsoft.NETCore.*` covers `Microsoft.NETCore.App.Runtime.linux-x64` but not `Microsoft.NETCoreApp` (`Microsoft.NETCore*` would cover both). Names and versions normalized per format (NuGet case-insensitive, PyPI PEP 503), prefixes too. Refused (the entry exempts nothing; a config warning, an error under `NORA_CONFIG_STRICT`): `*` alone, an empty prefix, `*` anywhere but the end of the name or twice, a version glob other than `*` (`1.*`). An exempt version still goes through the digest quarantine, the blocklist and `internal_namespaces` (the namespace filter runs before the chain and an internal ID is never proxied, so a pattern cannot pull an internal name from upstream), and is not hidden from metadata. Security: a pattern trusts a whole namespace on that registry's upstream with no cooldown, so keep it to first-party namespaces you would take on release day anyway (nuget.org reserves the `Microsoft.*` ID prefix to Microsoft). Reloaded on SIGHUP; each exemption logs `[SECURITY]` with the matching `rule` and counts in `nora_curation_min_age_allowed_total{registry}`; `nora curation explain nuget:<id>@<version>` prints the entry that exempts it.
- `curation.mode = "enforce"` + `min_release_age` also hides younger versions from proxied metadata, filtered on serve (cache keeps the upstream original): npm packument (full and `install-v1`; `latest` → newest allowed, other tags on hidden versions dropped), PyPI simple index (HTML + PEP 691, dated by `dates.json`), NuGet registration index/pages, flat-container `index.json`, search and autocomplete `?id=` (search reads only the newest registration page). Uses the upstream dates regardless of `trust_upstream_dates` (hiding cannot let a version through). Audit mode only logs, once per version per hour. Hosted, internal-namespace and `allow`-listed versions are not hidden.
- NuGet unlisted versions (registration `published` 1900-01-01; any year before 1950 or no date) are dated by their catalog leaf's `created` (`catalogEntry.@id`, fetched once from the upstream's origin, kept in `nuget/catalog/{id}/{version}.json`; not fetched when the registration leaf's `commitTimeStamp` is already past `min_release_age`). A proxied version still undated with `trust_upstream_dates` follows `curation.on_failure`: `closed` holds it as released now (403, hidden from metadata); `open` (still refused by config validation) leaves it to the quarantine. Hosted and internal-namespace versions are not dated.
- npm ownership (R2-18..21): versions published or imported here skip `min_release_age`; a package with local versions never fetches a tarball it lacks from an upstream, nor sends its name in `npm audit` while a namespace filter is active; publish attachments must be `<name>-<version>.tgz` and never replace a tarball published here (409; a proxied cached copy is replaced), and a failed publish is rolled back. A cached proxied packument keeps its `time` map in `npm/<name>/dates.json`, which the tarball date gates read instead of the packument.
- Web UI repo index: built in the background at startup and every 10 min (other processes' writes; hosted NuGet state documents still after `POST /api/v1/admin/reindex`), and after a write on the next read; a request waits at most 250 ms for a rebuild, then serves the previous index or an "indexing" state (`/simple/`: 503 + `Retry-After` before the first build). Hosted NuGet IDs come from the in-memory state documents, not a `nuget/hosted/` listing. Package detail pages take sizes from one listing of the package's prefix, not a `stat()` per version. `/favicon.ico` and `/ui/static/*` need no auth, also under `require_for_ui`. The upstream URL leak detector skips a registry's intentional pass-throughs, listed once in `metrics::UPSTREAM_PASSTHROUGH` (NuGet catalog0 `@id`s; npm `dist.attestations.url` on `/-/npm/v1/attestations/`, so `npm audit signatures` fetches provenance from npmjs directly); NoraUpstreamUrlLeak needs 5m.
- API tokens live in the storage backend (bucket in `storage.mode = s3`), not on the local disk: one immutable record per token at `.nora-tokens/<16hex>.json` (created with `put_if_absent`), last-use times in one `.nora-tokens/last_used.json` written by the 30 s flush (records are never rewritten, so a flush cannot resurrect a revoked token), cache-miss verify = one storage read; `auth.token_storage` (`NORA_AUTH_TOKEN_STORAGE`) is now the legacy directory whose `<16hex>.json` files each boot imports once (`.nora-tokens/legacy_imported.json` lists them, so a token revoked after its import stays revoked; an existing record is never overwritten; the files stay; a missing directory is fine); `nora backup` carries `.nora-tokens/` as storage keys and `nora restore` puts an older archive's `.nora-local/tokens/` records there.
- NuGet service index advertises `SearchQueryService` and `SearchAutocompleteService` bare and as `/3.0.0-beta`, `/3.0.0-rc`, `/3.5.0` (the api.nuget.org set): the NuGet client finds search only through `/3.0.0-beta`, so `dotnet package search` failed with "The source does not have a Search service!".
- The digest-quarantine ledger lives in the storage backend, not on the volume (so `storage.mode = s3` needs no PVC): one object per entry, `.nora-quarantine/<registry>/<digest>`, written with `put_if_absent` (first writer wins; a replica that loses the race adopts the stored `first_seen`), plus `.nora-quarantine-snapshot.json` (the map and `as_of`, rewritten at each start, which lists the prefix and GETs only entries the snapshot lacks, then drops >90 d entries with their objects); a `{storage.path}/quarantine.jsonl` is imported at every start (first line of a digest wins, original `first_seen`, file left in place); `nora backup`/`migrate` carry the entries, `nora restore` overwrites them (also from a legacy `.nora-local/quarantine.jsonl`) and drops the snapshot.

|---|---|---|---|

| People / CI (package clients) | `https://packages.maestra.io` `/nuget/`, `/npm/`, `/simple/` | `nra_` token as Bearer, `X-NuGet-ApiKey` or Basic password | the token's role |

| Anyone | public hostname, any other path | none: traefik routes only the registry prefixes and `/health`, `/ready` | n/a |

Update from upstream:
```sh
git fetch upstream && git checkout main && git merge --ff-only upstream/main && git push origin main
git checkout maestra/main && git merge main && git push origin maestra/main
```

Merge, not rebase: `maestra/main` is the default branch with open PRs on it, a rebase would force-push it and invalidate every branch cut from it; a merge resolves each upstream conflict once, in one commit.
Changes meant for upstream: branch from `main`, cherry-pick, open the PR against getnora-io/nora.

## CI and releases

- `.github/workflows/maestra-ci.yml`: on PRs into and pushes to `maestra/main` (RunsOn `pool=build`; every main commit gets its own run): `cargo fmt --check`, clippy `-D warnings` and `cargo test`, all `--locked`, for the default and the release (`--no-default-features`) feature sets; `cargo deny check advisories` against `deny.toml`; `helm chart`: helm unittest, `lint --strict` and `template` of `maestra/charts/nora` with default and `ci/maestra-values.yaml` values, plus the `deploy/` ↔ chart prometheus-rules identity check.
- `.github/workflows/maestra-release.yml`: tag `v<version>-maestra.<n>` (version = `Cargo.toml`) on `maestra/main` builds the upstream `Dockerfile` with `--build-arg CARGO_FEATURES=--no-default-features` (no rpm/deb) and pushes `515260921971.dkr.ecr.us-west-2.amazonaws.com/nora:<version>-maestra.<n>` via the Teleport image-push bot (token `image-push-github-actions-nora`, fluxcd `iota/us-iota-lw-kube-infra/teleport-maestra/operator-crs/image-push-tokens.yaml`). After the image it pushes the chart `maestra/charts/nora` to `oci://515260921971.dkr.ecr.us-west-2.amazonaws.com/charts/nora:<version>-maestra.<n>` (version = appVersion = image tag; the repository is created on first push). Last, job `release` (RunsOn `pool=small`, the only job with `contents: write`) creates or, on a re-run, updates the GitHub Release for the tag: notes generated since the previous `v*-maestra.*` tag plus the image and chart references with digests, marked latest only for the highest maestra tag. Re-run: `gh workflow run maestra-release.yml -f tag=<tag>`.
- `.github/workflows/maestra-sync-public-ids.yml`: daily 05:17 UTC and on dispatch (RunsOn `pool=small`): for the public `Mindbox.*` IDs in `maestra/scripts/import/public-ids.txt` imports every nuget.org version packages.maestra.io does not host yet (`enumerate.py --nuget-org-ids --missing-only`, then `import.py`; each package checked against the nuget.org catalog `packageHash`); red on any failed version. nora never proxies an ID it hosts and `curation.internal_namespaces` holds `mindbox.*`, so this is how their new releases arrive; a new public `Mindbox.*` ID resolves only once it is listed there (first run imports all its versions). Credential: the run's GitHub OIDC token (fluxcd nora role rule for `refs/heads/maestra/main`: `write`, `namespace_scope` `mindbox.*`), no stored secret.
- `.github/workflows/maestra-sync-artifactory-npm.yml`: hourly at :41 UTC and on dispatch (RunsOn `pool=small`): imports the `@mindbox-cloud/*` versions Artifactory `npm-local` has and packages.maestra.io does not (`enumerate.py --npm-missing-only`, then `import.py`; each tarball checked against the source `dist.integrity` before the push, so lockfiles stay valid; a nora dist-tag is never moved back); red on any failed version. GitLab pipelines still publish these libraries to Artifactory and their tags reach GitHub with the GitLab syncs, so semantic-release on GitHub never publishes those versions here (issues-maestra#1567: `frontend-visual-template-renderer` 12.x). Credentials: the Artifactory read token from the central Vault (jwt-github role `nora-artifactory-sync-github-ci`, `maestra/main` only) and the run's GitHub OIDC token (fluxcd nora role rule for `refs/heads/maestra/main`, `namespace_scope` `mindbox.*` and `@mindbox-cloud/*`).
- Third-party actions in `maestra-*.yml` are pinned by commit SHA (`# vX` comment), the helm-unittest plugin by release-tarball sha256.
- Our workflows carry a `maestra-` prefix so upstream merges never conflict on them. Upstream `Release`, `Post-Release Gate` and `PR Image Cleanup` target upstream's ghcr/self-hosted runners and are disabled in this repo (`gh workflow disable`); upstream `Release` would otherwise fire on our `v*` tags.

## Runbooks

`maestra/runbooks/<Alertname>.md`: agent-executable runbooks for packages.maestra.io, linked from the alert's `runbook_url` in `deploy/prometheus-rules.yml` (and its chart copy). The cluster's PrometheusRule picks up a new `runbook_url` only with the next chart release and fluxcd version bump. Exception: alerts in the fluxcd HelmRelease `metrics.prometheusRule.extraGroups` (group `nora-maestra`, e.g. `NoraOidcJwksRejections`) carry their `runbook_url` there and change with a fluxcd PR alone.
